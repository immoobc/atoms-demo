# 代码管理问题分析

> 分析日期：2026-11-12。依据为当前代码：`frontend/src/components/project/CodeView.tsx`、`ArtifactPanel.tsx`（`FileTree` / `CodePane` / `VersionsPane`）、`DiffView.tsx`、`frontend/src/lib/diff.ts`、`frontend/src/lib/projects.ts`、`backend/routers/project_workspace.py`。本文只做分析，没有修改功能代码。
>
> 背景：测评时“代码管理”得分 2/5，当时只能只读查看代码。之后补充了语法高亮、在线编辑后保存为新版本、版本对比、回滚和 zip 下载，但都**还没有在登录状态下做过端到端实测**。下面评估当前实现距离“代码管理”的预期还有哪些差距。

## 1. 结论摘要

当前实现能完成“看代码 → 改已有文件 → 存成新版本 → 对比 / 回滚 / 下载”这条最小链路，但和测评预期的“代码管理”（类似 IDE 加 Git 的体验）相比，主要差在以下五点，影响依次递减：

1. **没有 Git/GitHub 集成**：生成的项目只能下载 zip，不能推送或导出到仓库。
2. **文件树只读**：不能新建、删除、重命名文件。
3. **编辑器是 textarea 叠加高亮层**：缺少自动缩进、查找替换、括号匹配，Tab 后无法正常撤销等常见能力。
4. **提交说明不可填写**：版本历史无法追溯“谁、为什么、改了什么”。
5. **没有任何实测证据**：登录后的编辑、保存、对比、回滚、zip 下载都没有在浏览器里跑过。

预计按 P0 和 P1 完成改进并实测后，这一项可以回到 4/5 左右。

## 2. 问题清单（按优先级）

| 优先级 | # | 问题 | 现象 | 代码依据 | 对评分的影响 | 改进建议 |
|---|---|---|---|---|---|---|
| P0 | 1 | 没有 Git/GitHub 集成 | 应用内不能把生成的项目推送到仓库、创建仓库或查看提交记录，只能下载 zip | 前端只有 `downloadZip`（`lib/projects.ts`）；后端只有 `GET /runs/{id}/zip`，没有任何 git 相关接口 | 大：“代码管理”通常默认包含版本库对接，这是最直观的缺口 | 增加“推送到 GitHub”：用户在 Atoms Cloud 密钥里配置令牌，后端用 GitHub Contents/Git Data API 把某个版本的文件提交到指定仓库和分支，提交说明取版本备注，并记录回推得到的 commit 链接 |
| P0 | 2 | 文件树只读 | 不能新建、删除、重命名文件；编辑时只能修改模型已经生成的文件。例如模型漏掉 `app.js` 时，用户无法手动补上 | `FileTree` 只渲染 `onSelect`；`CodePane` 的 `drafts` 只修改已有键，没有任何增删入口 | 大：测评检查文件管理时，会直接判为“不支持” | 文件树增加新建、重命名、删除（右键或悬停菜单）；草稿结构支持增删键。后端 `_validate_files` 已有路径校验和 20 个文件的上限，可以直接复用 |
| P0 | 3 | 没有端到端实测证据 | 编辑保存、版本对比、回滚、zip 下载都只通过了 lint、build 和后端语法检查，没有在登录状态下跑过 | 见 `系统功能设计说明.md` 8.3 节 U6 | 大：评分依赖可演示的结果 | 充值 AI 余额并登录后，按照“生成 v1 → 编辑保存为 v2 → 对比 v1/v2 → 回滚 v1 生成 v3 → 下载 zip 并解压核对”的顺序实测，并截图留证 |
| P1 | 4 | 编辑器能力弱 | 有行号、语法高亮，Tab 插入两个空格；但没有 Shift+Tab 反缩进、回车自动缩进、括号补全或匹配、查找替换、折叠、多光标、错误提示。Tab 通过 `onChange` 拼接字符串实现，会打断浏览器原生撤销栈。每次按键都对整个文件重新高亮，大文件会卡顿 | `CodeView.tsx` 的 `CodeEditor`（textarea 叠在 `<pre>` 上）及其 `onKeyDown` | 中：测评会认为它“像普通文本框” | 换成 CodeMirror 6（体积小，自带撤销、查找、缩进、括号和折叠），保留现有主题配色；或者至少用 `execCommand('insertText')` 插入缩进，保住撤销栈 |
| P1 | 5 | 提交说明不可填，历史难以追溯 | 保存时备注自动生成为“手动编辑 a、b（基于 vN）”，用户不能填写；版本卡片不显示来源版本 `source_version`，也看不出某个版本基于哪个版本 | `CodePane.save` 固定拼接 note；后端 `POST /versions` 已经支持 `note`；`VersionsPane` 没有渲染 `dev_output.source_version` | 中 | 保存时弹出“提交说明”输入框；版本卡片显示“基于 vK”和改动文件数，必要时画出版本链 |
| P1 | 6 | 草稿容易丢失 | 编辑草稿只存在组件内存里，刷新或离开页面就会丢失，也没有“未保存离开”的提示；AI 流水线在运行时仍然可以编辑，基线可能已经过时 | `CodePane` 中 `drafts` 用 `useState`；没有 `beforeunload` 监听 | 中 | 把草稿按“项目 + 版本”存进 sessionStorage 或 localStorage；离开页面时提示；流水线运行时提示基线可能变化 |
| P2 | 7 | 版本对比有降级情况，展示方式单一 | 正常情况下是逐行 LCS diff。但当两个文件行数乘积超过 400 万时，降级为“整份删除 + 整份新增”，实际上变成整文件对比。只有统一视图，没有并排视图；没有行内（字词级）高亮；只能对比已保存的版本，不能对比草稿和当前版本 | `lib/diff.ts` 的 `MAX_CELLS` 及其降级分支；`DiffView.tsx` | 小到中 | 改用 Myers 算法（或 `diff` 包）来避免降级；增加并排视图和字词级高亮；编辑模式下提供“查看改动” |
| P2 | 8 | 回滚和下载的细节 | 链路完整：回滚生成新版本并保留历史，zip 由后端打包。但 zip 以 base64 放在 JSON 里返回，体积多约 33%；不能下载单个文件；最新的可用版本不能回滚，这是合理的，但界面没有说明原因，只有一个 title 提示 | `run_zip`、`rollback`（`project_workspace.py`）；`VersionsPane` | 小 | 改为直接返回 `application/zip` 流；增加单文件下载；禁用的按钮配上可见的说明文字 |
| P2 | 9 | 保存限制与产物形态 | 限制本身不算严（最多 20 个文件、每个不超过 300KB、必须有 index.html、文件名只能用 `[\w.\-/]`）。但 AI 流水线只生成最多 3 个文件，又不能新建文件，所以 20 个文件的上限实际上用不到；文件名不能含空格 | `_validate_files`；`DEV_SYSTEM` 中 3 个文件的约定 | 小 | 放开新建文件后，这些限制就有意义了；提示文案说明文件名规则；后续可以支持多文件或组件化产物 |
| P3 | 10 | 其他体验点 | 窄屏下文件树收起为下拉框，手机上编辑体验一般；没有文件内搜索或跨文件搜索；没有分支概念，版本只能线性发展 | `CodePane` 的 `sm:` 断点 | 小 | 增加全局搜索；分支可以放到 Git 集成之后再考虑 |

## 3. 已具备的能力（对照检查项）

| 检查项 | 当前情况 |
|---|---|
| 文件树 | ✅ 按目录分组、点选查看、改动圆点；❌ 新建、删除、重命名 |
| 编辑器 | ✅ 行号、Prism 高亮、Tab 缩进；❌ 自动缩进、查找、撤销完整性等（不是真正的代码编辑器） |
| 版本 | ✅ 每次保存或回滚都生成新版本，类型区分 AI / 手动 / 回滚，后端记录 `source_version`；❌ 自定义提交说明，前端不显示来源版本 |
| 版本对比 | ✅ 行级 LCS、增删统计、折叠无变化行；⚠️ 超大文件降级为整文件对比 |
| 回滚 | ✅ 生成新版本，保留历史，后续迭代以它为基线 |
| zip 下载 | ✅ 后端打包，文件名为“项目名-vN.zip” |
| 保存限制 | ✅ 合理，不算严格 |
| Git/GitHub | ❌ 没有 |
| 实测 | ❌ 登录后的全部操作都未验证 |

## 4. 建议的改进顺序

1. **P0**：推送到 GitHub；文件增删和重命名；登录后实测并截图。
2. **P1**：换用 CodeMirror 6；提交说明输入框和来源版本展示；草稿持久化和离开提示。
3. **P2/P3**：Myers diff 和并排视图；zip 改为流式下载、单文件下载；搜索。
